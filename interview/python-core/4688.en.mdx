# Lazy and and or operators: short-circuiting and returned values

## In short

`and` and `or` evaluate expressions from left to right and stop as soon as the result is known. This is short-circuiting. They do not necessarily return `True` or `False`: they return one of their operands, so they can both guard an operation and select a value.

## How to answer in an interview

The laziness of `and` and `or` means that the right side is not evaluated when the left side has already determined the result.

- `left and right` returns the first falsy operand; if every operand is truthy, it returns the last one.
- `left or right` returns the first truthy operand; if every operand is falsy, it returns the last one.
- That makes `user is not None and user.is_active` safe: the attribute is not read when `user` is `None`.
- In a condition, the result is converted to `bool`; outside one, remember that the returned value is an object, not just its truth value.

## How it works

For `and`, a falsy left operand already makes the whole expression falsy, so Python does not evaluate the right side:

```python
def load_profile():
    print("loading")
    return {"name": "Ada"}


cached = None
profile = cached and load_profile()
print(profile)
```

`load_profile` does not run, and `profile` receives `None`. `or` has the opposite behavior: if a value already exists, no fallback is needed.

```python
def read_default():
    print("reading default")
    return "guest"


name = "Ada"
display_name = name or read_default()
print(display_name)
```

Here `read_default` does not run either, and `display_name` is the string `"Ada"`, not a Boolean.

Laziness enables guard checks:

```python
user = None
can_edit = user is not None and user.get("role") == "editor"
print(can_edit)
```

Without the first part, calling `get` on `None` would raise `AttributeError`.

## Pitfalls

- `value or fallback` replaces not only `None`, but any valid falsy value: `0`, `""`, `[]`, or `False`. If only `None` needs replacing, use an explicit check.
- Do not put a required side effect on the right when it must always happen: short-circuiting can skip it.
- A chain such as `a and b and c` returns an operand, so `result is True` is usually the wrong test. Use `bool(result)` when a real flag is required.
- This is no substitute for a clear `if`: a short guard reads well, while complicated business logic written with `and` and `or` quickly becomes opaque.
